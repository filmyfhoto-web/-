→ หน้าจอ QR ที่เจ้าของร้านเห็น มาจากแท็บเก่า/แอปที่ติดตั้งไว้ (PWA) ที่ยังค้าง shell รุ่นก่อน
ไม่ใช่หน้าที่ระบบยังให้บริการอยู่ จึงไม่มีตัวไหนคอยเด้งหน้าให้

## จุดที่ "จะพัง" อยู่แล้วแม้เปิดหน้านั้นกลับมา

ในโค้ดที่ค้างอยู่ ตัวจับสัญญาณเรียลไทม์ผูกกับบรรทัดนี้:

```
const watchedLineUserId = readBinding()?.line_user_id || null;
if (!autoWatching || !watchedLineUserId) return;   // ไม่ subscribe
```

คนที่เปิดจากคอมและยังไม่เคยล็อกอิน LINE บนเครื่องนั้น จะไม่มี binding
→ ไม่เคย subscribe เรียลไทม์เลย เหลือแต่ polling ที่ถามด้วยตัวตนของเบราว์เซอร์เครื่องนั้น
ซึ่งไม่มีทางรู้ว่ามือถืออีกเครื่องเพิ่งกดเพิ่มเพื่อน — ต่อให้เรียลไทม์ทำงาน ก็ไม่ยิงมาที่เครื่องนี้
เพราะ topic คำนวณจาก LINE userId ที่เครื่องนี้ยังไม่รู้จัก
(ส่วน `subscribeLineLinked` เองยังถูกต้องดี ไม่ได้พังจากการแก้รอบก่อน)

## เสนอวิธีแก้

### ทางเลือก A (แนะนำ) — ลบซากที่ค้าง ไม่ต้องมีหน้า QR อีก
สอดคล้องกับนโยบายปัจจุบันที่ไม่บังคับผูก LINE แล้ว ลูกค้าสั่งซื้อได้ทันที

- ลบ `src/components/onboarding/OnboardingGate.tsx`
- ลบ/แทนที่เทสต์ `src/__tests__/onboarding-auto-recheck.test.ts` ด้วยเทสต์ยืนยันว่า
  เส้นทางลูกค้าไม่มีประตูกันอีกแล้ว
- ตรวจว่าไม่มี import ค้าง แล้วรันเทสต์ + build
- ให้เจ้าของร้าน "ล้างแคช/ถอนติดตั้งแล้วเปิดใหม่" หนึ่งครั้ง เพื่อให้หลุดจาก shell เก่า
  (โปรเจกต์มีกลไก `freshBuild` อยู่แล้ว จะตรวจเพิ่มว่าครอบหน้าลูกค้าด้วยหรือยัง)

### ทางเลือก B — เอาหน้า QR กลับมาให้ใช้ได้จริงบนคอม
ถ้ายังอยากได้ขั้นตอน "เพิ่มเพื่อนก่อนเข้าร้าน" ต้องแก้ที่รากคือ
คอมไม่รู้ว่าใครสแกน จึงต้องใส่รหัสอ้างอิงลง QR:

- สร้างรหัสรอบละ 1 ค่า (session code) ฝังใน URL ของ QR
- ให้ฝั่ง `line-webhook` ตอนรับ follow ยิง broadcast ด้วย topic ที่คำนวณจากรหัสนั้น
- หน้าคอม subscribe ด้วยรหัสของตัวเอง (ไม่ต้องมี line_user_id ก่อน) + polling สำรอง
- งานนี้ใหญ่กว่า A มาก (แตะ edge function + ตาราง session + หน้าเว็บ)

รอเลือกก่อนว่าจะเอาทาง A หรือ B — ยังไม่แก้โค้ดใด ๆ

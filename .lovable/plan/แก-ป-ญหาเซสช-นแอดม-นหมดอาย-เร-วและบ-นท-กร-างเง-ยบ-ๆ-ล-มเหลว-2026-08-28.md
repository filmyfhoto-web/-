# แก้ปัญหาเซสชันแอดมินหมดอายุเร็วและบันทึกร่างเงียบ ๆ ล้มเหลว

## สถานะที่ตรวจพบ
- ค่า access-token expiry ของ backend ปัจจุบันคือ `3600` วินาที หรือ 1 ชั่วโมง ไม่ใช่ 30 นาทีตามที่รายงานโดยตรง
- client auth เปิด `persistSession: true` และ `autoRefreshToken: true` อยู่แล้วใน client ที่สร้างอัตโนมัติ
- มี `startSessionKeepAlive()` ใน `AuthContext` ซึ่งเรียก `startAutoRefresh()` และ `refreshSession()` เมื่อแท็บ/แอปกลับมา visible, focus, pageshow หรือ online และจะ refresh เมื่อ token เหลือไม่ถึง 5 นาที
- ยังไม่พบ custom idle timer หรือโค้ดที่ `signOut()` หลังไม่ใช้งาน 30 นาที จึงต้องแยกตรวจระหว่าง access-token อายุ 1 ชั่วโมง, policy inactivity ของ backend และปัญหา mobile/PWA ที่ timer หยุดเมื่อถูกพัก
- ระบบบันทึกร่าง `src/pages/receipts/lib/drafts.ts` เก็บ localStorage ก่อนเสมอ แต่การบันทึกฐานข้อมูลจับ error แล้วเงียบไว้ หาก session หมด/refresh ไม่สำเร็จหรือ RLS ปฏิเสธ จึงมีความเป็นไปได้ที่ผู้ใช้เห็นเหมือนบันทึกร่างไม่สำเร็จโดยไม่มีข้อความแจ้ง

## แนวทางที่เสนอ
1. คง access-token expiry ที่ 1 ชั่วโมงเป็นค่าเริ่มต้น ไม่ยืด token อายุยาวเกินจำเป็น และใช้ refresh token ต่ออายุเบื้องหลังระหว่างที่ผู้ใช้ยังใช้งานอยู่
2. ตรวจและปรับ policy inactivity ของ Lovable Cloud ให้เหมาะกับงานแอดมินเป็นประมาณ 8 ชั่วโมง (หนึ่งกะทำงาน) หากค่าปัจจุบันเป็น 30 นาที โดยยังคงให้ session ต้องกลับมา login ใหม่เมื่อไม่มีการใช้งานนานจริงหรือ refresh token หมดอายุ
3. ปรับ `sessionKeepAlive` ให้มีการตรวจ session แบบเบา ๆ ตามช่วงเวลาที่กำหนดขณะหน้าแอดมินเปิดอยู่ ไม่พึ่งเฉพาะ browser visibility events และยังหยุด/ผ่อนการทำงานเมื่อหน้าไม่ active เพื่อไม่ทำให้เกิด request ที่ไม่จำเป็น
4. เพิ่มการจัดการผลลัพธ์ของ `saveDraft` ให้แยกชัดเจนระหว่าง:
   - บันทึก localStorage สำเร็จ แต่ฐานข้อมูลยังไม่สำเร็จ — ไม่ทำให้ข้อมูลผู้ใช้หาย
   - session หมดอายุ — พยายาม refresh หนึ่งครั้ง แล้วลองบันทึกฐานข้อมูลใหม่แบบ bounded ไม่วนซ้ำ
   - error อื่น เช่น permission/network — แสดงสถานะหรือ callback ให้หน้าปัจจุบันแจ้งผู้ใช้แทนการกลืน error เงียบ ๆ
5. ตรวจจุดเรียก `saveDraft` ที่สำคัญของเอกสาร/POS/settings ให้ใช้ผลลัพธ์เดียวกัน และไม่แสดงข้อความว่า “บันทึกแล้ว” หากสำเร็จเพียง localStorage แต่ควรบอกว่าเก็บไว้ในเครื่องและจะ sync เมื่อกลับมาออนไลน์/เข้าสู่ระบบ
6. เพิ่มเทสต์สำหรับ access-token ใกล้หมดอายุ, refresh สำเร็จ/ล้มเหลว, session ไม่มี, draft DB ล้มแต่ localStorage ยังอยู่ และไม่ retry เกินหนึ่งรอบ

## ไฟล์ที่คาดว่าจะแก้
- `src/lib/sessionKeepAlive.ts` — ปรับการต่ออายุขณะใช้งานและ lifecycle handling
- `src/contexts/AuthContext.tsx` — ผูก lifecycle/cleanup ของ keep-alive ให้ชัดเจน โดยไม่เปลี่ยน role หรือ auth guard
- `src/pages/receipts/lib/drafts.ts` — เปลี่ยนจากกลืน error เป็นผลลัพธ์สถานะที่เรียกใช้ได้ และทำ bounded refresh/retry
- จุดเรียก `saveDraft` ที่พบจากการตรวจจริง เช่นหน้าเอกสาร, POS และ settings — ปรับเฉพาะข้อความ/การแสดงสถานะที่เกี่ยวข้องกับผลการบันทึกร่าง
- เทสต์ใหม่หรือเทสต์เดิมที่เกี่ยวข้องกับ `sessionKeepAlive` และ `drafts`
- การตั้งค่า session inactivity ของ backend — ทำผ่านการตั้งค่าที่รองรับของ Lovable Cloud เท่านั้น ไม่แก้ schema ตาราง auth และไม่เก็บ token เพิ่มใน localStorage เอง

## ค่าที่เสนอและเหตุผล
- Access token: คง `3600` วินาที (1 ชั่วโมง) เพื่อจำกัดผลกระทบหาก token รั่ว
- Auto refresh: เปิดต่อไป และ refresh ก่อนหมดอายุ 5 นาที รวมถึงตรวจเป็นระยะขณะหน้าแอดมิน active
- Inactivity timeout: เสนอประมาณ 8 ชั่วโมง หากระบบรองรับการตั้งค่านี้ใน Cloud; เป็นเวลาประมาณหนึ่งกะ ไม่ทำให้ต้อง login ใหม่จากการพักสั้น ๆ แต่ยังบังคับ login ใหม่หลังไม่ใช้งานข้ามวัน/นานจริง
- Refresh failure: ไม่วน retry ไม่จำกัด; ให้ลองแบบ bounded ครั้งเดียวหลังตรวจ session แล้วเปลี่ยนเป็นสถานะต้องเข้าสู่ระบบเมื่อยืนยันว่า refresh ใช้ไม่ได้

## ความเสี่ยงและการป้องกัน
- ยืด inactivity timeout ทำให้เครื่องแอดมินที่เปิดค้างมี session อยู่นานขึ้น: จำกัดเฉพาะช่วงหนึ่งกะ, คง access token อายุ 1 ชั่วโมง และไม่ลด role/RLS checks
- refresh ถี่เกินไปอาจเพิ่ม request และชน rate limit: ใช้ timer เฉพาะหน้า active, dedupe refresh ที่กำลังทำอยู่ และ refresh เฉพาะเมื่อใกล้หมดอายุ
- retry บันทึกร่างซ้ำอาจเกิด duplicate: ใช้ upsert เดิมและจำกัดหนึ่ง retry ต่อการบันทึกหนึ่งครั้ง
- การซ่อน error เดิมช่วยให้ UI ไม่ล้มแต่ทำให้เจ้าของร้านไม่รู้สถานะ: เปลี่ยนเป็นสถานะที่บอกได้ว่าบันทึกในเครื่องหรือ sync แล้ว โดยไม่เปิดเผย token/ข้อมูลลับ
- การเปลี่ยนค่า inactivity policy อาจต้องใช้การตั้งค่า backend ที่รองรับ หาก Cloud ไม่เปิดให้ตั้งจากช่องทางที่ปลอดภัย จะคงค่าเดิมและแก้เฉพาะ auto-refresh/lifecycle/draft feedback แทน ไม่แตะตาราง auth เอง

## การตรวจรับหลังอนุมัติ
- ตรวจค่า session policy จริงอีกครั้งก่อนเปลี่ยน และบันทึกค่าก่อน/หลังโดยไม่เปิดเผย token
- จำลอง token ใกล้หมดอายุและกลับเข้าแท็บ/แอป ให้ต่ออายุได้โดยไม่เด้งไป login
- จำลอง session หมดจริง ให้ถูกพาไป login อย่างชัดเจนและไม่วน redirect
- เปิดหน้าเอกสาร/POS/settings ทิ้งไว้เกินช่วง refresh แล้วแก้ไขและบันทึกร่าง ตรวจว่ามีสถานะ sync ที่ถูกต้อง
- จำลอง DB/RLS/network error ตรวจว่า local draft ยังโหลดกลับมาได้และ UI ไม่รายงานว่าสำเร็จเกินจริง
- รัน targeted tests, security check ตาม workflow ของโปรเจกต์ และตรวจ build log ล่าสุดก่อนสรุปผล
